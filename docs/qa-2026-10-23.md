## Fixes in this QA release

- Recover first-load unique-key races without replacing saved settings.
- Keep optional menu/email outages from crashing the dashboard while preserving
  Shopify authentication recovery responses.
- Provide a recoverable dashboard error view and preserve the original sync
  error if saving its failure status also fails.
- Preserve explicitly empty section selections, normalize settings, and commit
  settings with the completed snapshot.
- Reject failed/partial GraphQL responses and stalled pagination.
- Escape merchant HTML and Liquid delimiters, reject action URLs, and tolerate
  malformed optional dates.
- Publish Shopify content before committing the database snapshot, preserving
  the last database snapshot if Shopify rejects publication.
- Publish chunks, configuration, and manifest in one atomic Shopify mutation.
  Preflight the 25-field, JSON-size, and request-size limits before writing;
  unusually large data receives a recoverable size error instead of a partial
  theme update. Both ordinary and multilingual 5,000-link fixtures fit.
- Correct empty-sitemap and password-protection detection; bound check duration.
- Prevent proxy access after the installed session has gone away.
- Preserve failed remote erasure for webhook retry and keep unsubscribe retry
  on the unsubscribe path.
- Handle malformed signed email-provider payloads without an application crash.
- Render large theme chunks within Shopify's loop limit and honor saved false
  display settings.

Delayed or retried cleanup is a **code-identified risk, not a failure observed
in this test**: the current cleanup handlers delete by store domain and have no
installation-generation guard. Shopify's [2026-04 shop/redact reference](https://shopify.dev/docs/api/webhooks/2026-04?accordionItem=webhooks-shop-redact)
states that the normal redaction event is not emitted after the app is
reinstalled; a normal fast reinstall cancels that scheduled redaction. This
qualifies the earlier broad warning: it is not an assertion that every rapid
reinstall receives shop/redact. Already delayed/retried cleanup has no local
generation guard. No speculative lifecycle or schema change was included.

Shopify publication and database saving are separate systems: a lost response
after Shopify commits, or a later database failure, can leave a newer theme
snapshot than the database-backed proxy. The app reports the operation as failed
and a successful generation reconciles them; this patch does not claim a
distributed transaction across Shopify and the database.

## Delayed cleanup hardening follow-up (release pending)

This follow-up replaces the unguarded cleanup behavior described in the earlier
released-baseline risk above. Cleanup and the official session-storage adapter
now serialize operations with the same database shop lock. A current offline
session verified against Shopify as active preserves the installation. A 401
permits erasure only when the current credential fingerprint was previously
recorded through a fresh verified SDK grant. Legacy credentials, credential
rotation, missing scopes, expired or blank tokens, and uncertain responses fail
closed. Cleanup does not attempt a background refresh or fall back to deleting
data after a timer expires. SDK invalidation retains uncertain credentials and
sets a reauthentication sentinel so a signed merchant request can obtain a fresh
grant without stale authentication writes replacing a newer session.

`AppOperationLock.lastCleanupStatus` and `lastCleanupAt` retain a diagnostic:

| Status | Meaning and next action |
| --- | --- |
| `ACTIVE_INSTALLATION` | Shopify verified the current installation; cleanup was skipped. |
| `ERASED` | Provider cleanup completed or was unnecessary, then tenant sitemap and session rows were erased. |
| `PROVIDER_ERASURE_PENDING` | A provider retirement intent is prepared or a provider request needs retry; sessions and sitemap remain intact. |
| `REAUTHENTICATION_REQUIRED` | Credentials are blank, expired, or within the SDK refresh window; obtain a fresh merchant grant before another destructive decision. |
| `SCOPE_EXCHANGE_REQUIRED` | Required scopes are absent; the normal merchant authorization flow must resolve them. |
| `CREDENTIAL_EPOCH_UNVERIFIED` | The current secret/credential pairing has not been verified through a fresh grant. |
| `VERIFICATION_UNAVAILABLE` | Installation verification was inconclusive; retry after the service recovers. |
| `CLEANUP_RETRY_REQUIRED` | The cleanup transaction failed; tenant data was rolled back and the failure requires retry. |

Shopify retries can end before an ambiguous installation becomes verifiable.
Operators must review unresolved statuses and reconcile retained data manually
when needed. There is no automatic destructive fallback and no claim that this
code alone completes every privacy-erasure obligation after retry exhaustion.

Marketing writes and provider synchronization take the shop lock followed by
sorted email locks in the same transaction. Provider contact callbacks take an
email lock only. Cleanup commits the immutable provider contact ID before any
DELETE is dispatched; the first staging delivery deliberately returns 503 after
commit. A later transaction retires that ID. Failed or uncertain erasure retains
the marker, and fresh activation drains older pending IDs before creating or
reactivating a contact. A shared contact already confirmed for another subscribed
shop is preserved; a fresh local consent that has not synchronized does not
discard an old pending retirement. Contact callbacks require the provider ID and
cannot apply an old-ID deletion event to its replacement merely by email, or
cancel a newer local consent that has not yet synchronized with the provider.

Provider requests use an abort signal with a one-second deadline. An abort is
not proof that the remote request stopped; a late DELETE still addresses only
the retired immutable ID. Provider behavior in these tests is mocked, including
late completion. No real welcome email, Resend mutation, or provider-delivery
latency has been exercised by this follow-up.

Two additive migrations are required before releasing this code:
`20261024000000_app_operation_lock` adds lock/diagnostic storage and
`20261024010000_marketing_erasure_generation` adds provider identity, activation
proof, and pending-erasure columns/indexes. The latter backfills the current
email for synchronized provider IDs and activation proof only for previously
synchronized subscribed rows. Unknown legacy ID/email associations are resolved
by a nondestructive provider lookup and committed before taking the actual old
email lock in a later retirement transaction. Neither migration deletes
application data. The local QA work
has not applied these migrations to production.
